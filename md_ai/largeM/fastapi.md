# 1.FastAPI + 异步任务队列（以 Celery 为例）

作为一个 C++ 工程师，你一定会非常关心 **CPU 时间片到底花在了哪个线程/进程上**。

在 **FastAPI + 异步任务队列（以 Celery 为例）** 的架构中，任务的耗时工作其实被分流到了两个完全不同的地方，取决于任务的类型：**IO 密集型** 还是 **计算密集型**。

---

## 1. 架构全景：分工明确

这个架构本质上是 **“前台接待 + 后台工厂”**。

* **FastAPI（前台）：** 运行在 **主线程** 的事件循环（Event Loop）中。
* **Celery Worker（后台）：** 运行在 **独立的进程（Process）** 中，完全脱离 FastAPI 的进程空间。

---

## 2. 耗时工作到底在哪处理？

我们将耗时工作分为两种场景来讨论：

### 场景 A：IO 密集型（等待大模型 API 返回）

这是你目前最常见的场景：调用百度千帆 API。

1. **在 FastAPI 中处理：**
* 如果你在 FastAPI 路由里写 `await qianfan.call()`，耗时工作实际上是在 **操作系统的内核网络栈** 里处理的。
* **线程归属：** 主线程。但主线程并不“干活”，它只是在等待网卡中断。此时主线程会切去处理别的请求。
* **这种方式不叫“耗时处理”，叫“耗时等待”。**


2. **在 Celery 异步队列中处理：**
* 如果你把推理请求扔给 Celery，FastAPI 会立即返回 `task_id`。
* **执行线程：** 任务会在 **Celery Worker 的某个工作进程/线程** 中执行。



### 场景 B：计算/处理密集型（大批量文档解析、清洗）

这是真正的“耗时工作”（占满 CPU）。

1. **绝不能在 FastAPI 主线程做：**
* 如果你在 `async def` 里写一个 `for` 循环处理 1GB 的文本，主线程会被卡死（GIL 锁死），整个 API 服务将无法响应任何新请求。


2. **必须在 Celery Worker 中做：**
* **执行线程：** Celery 默认开启多进程模式（Prefork）。
* **物理归属：** 任务运行在 **Celery 开启的子进程** 中。每个子进程都有独立的 Python 解释器和 GIL，能够利用多核 CPU。



---

## 3. 线程/进程交互流程图

当你提交一个“行业智能体批量推理”任务时：

1. **用户** 发送请求到 **FastAPI**。
2. **FastAPI (主线程)** 接收请求，简单校验数据（Pydantic 负责）。
3. **FastAPI (主线程)** 将任务描述（JSON）序列化后塞进 **Redis (Broker)**。
4. **FastAPI (主线程)** 立即返回 `{"status": "queued"}` 给用户。**主线程释放，继续接待别人。**
5. **Celery Worker (独立进程)** 监测到 Redis 有新任务，通过 `os.fork()` 出来的子进程捞取任务。
6. **Worker 子进程** 开始跑耗时逻辑：
    * 解析 PDF（CPU 密集）。
    * 循环调用模型 API（IO 密集）。
7. **Worker 子进程** 将最终结果写入 **Result Backend**（如数据库）。

---

## 4. 给 C++ 工程师的工程总结

* **FastAPI 进程：** 只是一个“分发器”。它的主线程（Event Loop）绝对不能跑耗时长的 CPU 算力逻辑。
* **Celery 进程：** 才是真正的“劳动力”。
* 如果你有 4 核 CPU，通常会启动一个 Celery 实例，包含 4 个 **Worker 进程**。
* 每个任务在其中一个进程的 **MainThread** 里运行。



**关键点：**
由于 Python 的 GIL（全局解释器锁）存在，单进程内的多线程无法利用多核。所以处理耗时任务时，我们通常使用 **Celery 的进程池（Prefork）**。

在你的代码里，你会这样区分：

* **轻量操作：** 查看日志、修改智能体配置 -> 直接写在 FastAPI `async def` 里。
