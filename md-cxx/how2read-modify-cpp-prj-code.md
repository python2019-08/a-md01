# ch01.C++ 开源项目代码如何快速学习并能修改

## 核心一句话
**快速看懂、还能改C++开源项目，不是逐行读完，是「先建立可验证的最小闭环 → 锁定你要修改的范围 → 小改+反复调试验证」。**
你之前的思路（编译跑通、看main、看线程协作、看核心数据结构）是很好的基础，但是要加上「修改导向」，而不是单纯读代码。

> 目标分层：
> 看懂 = 知道它怎么跑；
> 能改 = 知道改哪、改完怎么验证、知道改动的副作用。

下面这套流程，专门适配你现在看的这类大型C++项目（Valhalla、路由引擎、服务器、多线程计算类）。

## 阶段1：准备环境（最重要，很多人卡在这里）
> 原则：**没有能跑、能调试的版本，不要深度读代码**
1. **切稳定release版本，不要在master啃**
master一直在迭代，随时有未完成代码，改了之后一会就冲突。
2. 编译必须带上debug符号：`-g`，优化级别调低（O0/O1）
   - O2会把变量优化掉，gdb断点、看变量很难受；
   - 保留一份release版本用来对比性能。
3. 准备最小demo / CLI示例，**一条命令就能触发核心逻辑**
   比如Valhalla：一条简单路由请求，输入起点终点，输出路径。
   好处：你后面每次小改动，都用这个demo快速验证，不用搭复杂测试。
4. 准备工具（C++源码阅读三件套）
   - IDE：CLion（最强），或者VSCode+ccls/clangd，**能跳转、看调用关系、看类继承**；
   - 调试器：gdb/lldb，断点、看线程栈、backtrace；
   - 搜索：全局文本搜索（ripgrep），看结构体/函数在哪里读、哪里写。

✅ 这个阶段输出：**一个可以稳定复现、10秒跑完的最小case**。

## 阶段2：宏观摸底（1~2小时，不要扎进细节）
目标：画出一张极简架构图，回答这5个问题，不用看懂实现：
1. 目录怎么分？哪些模块？（Valhalla：baldr瓦片、sif通行规则、thor寻路、worker调度）
2. 程序入口main做了什么？哪些组件被初始化？线程池、缓存、存储、配置？
3. 一条请求的**完整数据流是什么**？（请求输入 → 分发 → worker → 读数据结构(NodeInfo) → 算法 → 返回）
4. 并发模型：有几类线程？任务怎么传递？（锁队列/无锁/future/回调）共享数据是谁、谁保护？
5. 配置文件、外部数据（瓦片文件）作用是什么？

> 实操技巧：
> main不要逐行看，只做标记：
> 哪些是基础设施（日志、内存、线程池），哪些是业务核心（寻路、坐标解码）。
> 基础设施先标记【暂时不看】。

❌ 禁忌：一上来就点开NodeInfo、一堆位域、模板，死磕底层。

## 阶段3：定向溯源（找到你要改的地方，这一步是核心）
你改代码，一定是为了一个具体需求：
比如：修改代价计算、增加一种通行权限、修改瓦片坐标解码逻辑、调整线程池参数。
> **不要通读整个项目，从【输入输出反向溯源】**

两种溯源方式，结合使用：
### 方式A：动态追踪（你喜欢的方式，适合流程、线程、调度）
1. 在最小demo跑通的链路里，找到输出点；
2. 在关键函数打断点，跟着一条请求走一遍；
3. 记录：调用栈、经过的类、传入的数据结构；
> 重点：**只盯一条请求，不要同时看多条并发请求**，不然时序直接乱掉。

### 方式B：静态搜索溯源（适合改数据结构、算法、编码，比如NodeInfo）
1. 找到目标结构体/函数；
2. 先搜：**哪里读它、哪里写它、序列化/反序列化在哪**
   ```
   rg NodeInfo
   ```
3. 区分：
   - 只读：只是解析（解码坐标）
   - 修改：写入持久化（写瓦片）
   - 多处共用：改动这里会影响所有调用方（风险高）

👉 非常重要的判断：**这个改动是局部的，还是渗透全链路？**
- 局部：只改thor里面A*的代价函数，只影响寻路；风险低，适合新手上手；
- 底层：修改NodeInfo内存布局、瓦片存储格式 → 所有读瓦片、写瓦片代码都要同步改，兼容性风险巨大（你前面看的位域就是这种）。

> 新手入门修改优先选【局部改动】，不要一上来碰底层存储结构。

## 阶段4：小步修改 + 增量验证（能改、改对的关键）
黄金法则：**一次只改一件事，改完立刻跑最小case**
流程模板：
1. 先写一个【预期结果】：改完之后输出应该变成什么样；
2. 只改一小块代码；
3. 编译，跑最小demo；
4. 对比输出，判断是否符合预期；
5. 如果不对：断点回溯，看哪一步数据和你想象不一样；
6. 稳定之后，再加更多测试case（边界case）。

### 改C++开源项目高频踩坑
1. **不要直接改底层公共结构，除非你看懂全部序列化逻辑**
像NodeInfo这种写入磁盘的二进制结构：改位域、改成员，旧瓦片文件直接无法解析，兼容性爆炸。
2. 并发代码改动：改队列、锁、线程逻辑，**不能只看单次跑通**，要多跑、压力测试，容易出现偶现死锁、数据竞争；
3. 回调、lambda捕获、生命周期：改回调逻辑非常容易悬引用；
4. 配置驱动项目：很多行为不是写死在代码里，是配置控制，先确认是不是改配置就能实现，根本不用改C++代码！

## 阶段5：理解依赖与副作用（进阶，防止改出隐性bug）
改完跑通，不等于改对。你要回答：
- 这个函数/类被多少地方调用？（IDE看caller）
- 有没有多线程同时访问？有没有锁保护？
- 这个数据会不会缓存？改了计算逻辑，缓存要不要清？
- 有没有持久化输出？会不会影响文件格式？
- 有没有对外API？改动会不会破坏API，影响其他依赖这个库的程序？

> 开源项目里很多bug不是改的地方错了，是**不知道别的模块也依赖这块逻辑**。

## 阶段6：学习路线两种版本，按需选
### 路线1：你现在的偏好（动态优先，适合调度、线程、请求链路）
编译跑通 → 最小demo → main看组件初始化 → 跟踪单条请求链路（线程+任务传递）→ 定位修改点 → 小改验证 → 回头精读用到的核心类（NodeInfo等）

✅ 适合：路由引擎、服务、多线程计算项目（Valhalla）

### 路线2：数据优先（适合算法、存储、编解码）
读文档/架构 → 模块目录 → 核心结构体、数据格式 → 序列化/反序列化 → 算法逻辑 → 调度线程
✅ 适合：数据库、编解码、文件格式类项目

## 阶段7：长期积累，快速读懂同类项目
看完一个项目后，沉淀3份笔记（不用很长）
1. 并发模型：线程怎么分工、任务传递方式（std::queue/无锁/future）
2. 核心数据模型：有哪些核心struct，数据流向
3. 扩展点：这个项目设计上哪些地方是预留修改点（插件、回调、虚函数、策略类）

> 很多成熟开源项目，作者本身就预留了扩展点（比如代价函数做成策略模式），你直接新增策略类就可以，不用硬改主干逻辑！这个是最高级的改法。

## 一个极简实操例子（套到Valhalla）
需求：修改寻路时某种道路的通行代价
1. 准备：一条简单路线demo；
2. 溯源：断点找到代价计算入口，定位到sif模块里cost函数；
3. 看：这个函数是不是单线程调用？输入是什么？只被寻路算法调用？
4. 小改：修改代价公式；
5. 验证：跑demo，看路径是否变化；
6. 补充：多case测试不同道路；
7. 记录：这个改动只影响A*搜索，不修改瓦片存储，无兼容性问题。

## 避坑清单（血泪总结）
1. ❌ 不要把整个项目看完再动手改，看不完，而且看完也容易忘；**边改边读，按需读**
2. ❌ 不要一上来改底层二进制存储、锁、无锁队列（改动范围极大）
3. ❌ 不要只看静态代码，不跑调试；C++并发代码静态很难看出时序问题
4. ✅ 优先找项目自带的单元测试，单元测试是最好的阅读材料和回归工具！很多开源项目有test文件夹
5. ✅ 读别人的PR！开源项目的pull request是最好的学习素材：别人是怎么改、改哪里、为什么改

## 给你一个落地建议
如果你现在目标就是Valhalla：
先从**修改通行代价、新增一种通行标记**这种局部改动入手，不要碰NodeInfo瓦片存储结构。等你熟练了链路之后，再去碰底层编码。
