# 1.add_library()  指定了 STATIC、SHARED 或 MODULE ,区别

在 CMake 中，`add_library()` 命令通过指定 `STATIC`、`SHARED` 或 `MODULE` 关键字，可以明确生成不同类型的库文件，它们的核心区别体现在**链接方式、文件格式、使用场景**等方面：


### 1. `STATIC`（静态库）
- **定义**：将代码编译为独立的静态库文件，链接时会被完整复制到最终可执行文件中。
- **文件格式**：
  - Windows：`.lib`
  - Linux/macOS：`.a`
- **特点**：
  - 可执行文件包含库的完整代码，运行时不依赖外部库文件。
  - 编译后可执行文件体积较大，但加载速度快。
  - 若静态库更新，依赖它的可执行文件需要重新编译链接。
- **适用场景**：
  - 小型库或工具类代码，希望简化部署（无需额外分发库文件）。
  - 对运行时性能要求较高的场景。
- **示例**：
  ```cmake
  add_library(my_static_lib STATIC src/file1.cpp src/file2.cpp)
  ```


### 2. `SHARED`（共享库/动态链接库）
- **定义**：生成动态链接库，链接时仅在可执行文件中记录库的引用，运行时才加载库文件。
- **文件格式**：
  - Windows：`.dll`（伴随 `.lib` 导入库）
  - Linux：`.so`（shared object）
  - macOS：`.dylib`
- **特点**：
  - 库文件独立存在，多个程序可共享同一份库，节省磁盘空间。
  - 可执行文件体积小，但运行时需确保库文件存在且路径正确。
  - 库更新后，无需重新编译依赖它的可执行文件（需保证接口兼容）。
- **适用场景**：
  - 大型库或被多个程序共享的组件（如系统库、框架）。
  - 需要动态更新功能（如插件框架的核心库）。
- **注意**：
  - Windows 下需显式处理符号导出（`__declspec(dllexport)`）和导入（`__declspec(dllimport)`）。
  - 跨平台项目需注意库的安装路径和运行时查找机制。
- **示例**：
  ```cmake
  add_library(my_shared_lib SHARED src/file1.cpp src/file2.cpp)
  ```


### 3. `MODULE`（模块库）
- **定义**：生成一种特殊的动态库，主要用于**动态加载**（而非链接时依赖），通常作为插件使用。
- **文件格式**：与 `SHARED` 相同（如 Linux 下 `.so`，Windows 下 `.dll`）。
- **特点**：
  - 不被链接到可执行文件中，而是通过 `dlopen()`（Linux）、`LoadLibrary()`（Windows）等函数动态加载。
  - 无需在编译时知道库的存在，适合扩展程序功能（如插件系统）。
- **适用场景**：
  - 插件系统（如浏览器插件、IDE 扩展）。
  - 需要动态扩展功能，且编译时无法确定具体模块的场景。
- **与 `SHARED` 的区别**：
  - `SHARED` 库在链接时被依赖，程序启动时自动加载；`MODULE` 库在运行时手动加载。
  - CMake 中 `MODULE` 库不会被 `target_link_libraries()` 链接，而是通过其他方式加载。
- **示例**：
  ```cmake
  add_library(my_plugin MODULE src/plugin.cpp)
  ```


### 总结对比表
| 类型    | 链接方式       | 运行时依赖 | 文件格式               | 核心用途                     |
|---------|----------------|------------|------------------------|------------------------------|
| `STATIC` | 编译时完全嵌入 | 无         | `.a`（Linux）、`.lib`（Windows） | 简化部署、提升加载速度       |
| `SHARED` | 编译时记录引用 | 依赖库文件 | `.so`、`.dll`、`.dylib` | 资源共享、动态更新           |
| `MODULE` | 运行时动态加载 | 按需加载   | 同 `SHARED`            | 插件扩展、动态功能扩展       |


通过选择合适的库类型，可以平衡程序的体积、部署复杂度和扩展性，这在大型项目或跨平台开发中尤为重要。

# 2.SHARED生成的动态库可以当作module库动态加载

是的，`SHARED` 类型生成的动态库**可以当作模块库（类似 `MODULE` 库）进行动态加载**，但两者在设计意图和 CMake 的处理方式上存在细微差异。


### 核心结论
- **技术可行性**：`SHARED` 动态库完全支持通过 `dlopen()`（Linux/macOS）、`LoadLibrary()`（Windows）等系统调用动态加载（无需在编译时链接），功能上与 `MODULE` 库一致。
- **CMake 层面的区别**：`MODULE` 是 CMake 对“仅用于动态加载的库”的**语义标记**，而 `SHARED` 更偏向“既可以链接也可以动态加载”的通用动态库。


### 具体差异与联系
1. **链接行为**  
   - `SHARED` 库可以被 `target_link_libraries()` 链接到可执行文件中（编译时确定依赖），也可以在运行时动态加载。  
   - `MODULE` 库在 CMake 中被明确标记为“不用于链接”，`target_link_libraries()` 不会链接它，仅用于动态加载场景。

2. **使用场景重叠**  
   若一个 `SHARED` 库不被任何目标链接，仅通过动态加载接口（如 `dlopen`）使用，其实际效果与 `MODULE` 库完全一致。例如：  
   ```cmake
   # 生成 SHARED 库，但不链接到任何目标，仅用于动态加载
   add_library(my_shared_lib SHARED src/plugin.cpp)
   
   # 生成 MODULE 库，语义上明确用于动态加载
   add_library(my_module_lib MODULE src/plugin.cpp)
   ```  
   这两种库都可以通过 `dlopen("./libmy_shared_lib.so")` 或 `dlopen("./libmy_module_lib.so")` 动态加载。

3. **平台兼容性**  
   在多数平台（Linux/macOS/Windows）上，`SHARED` 和 `MODULE` 生成的库文件格式完全相同（如 `.so`、`.dll`），动态加载的代码也完全通用。  
   唯一例外是 macOS 上的某些特殊处理，但实际使用中差异可忽略。


### 建议用法
- 若库**仅用于动态加载**（如插件），优先使用 `MODULE`，通过 CMake 的语义标记明确其用途，使项目结构更清晰。  
- 若库**既需要被链接**（供主程序直接调用）**又需要被动态加载**（供插件系统扩展），则必须使用 `SHARED`。


总之，`SHARED` 库在技术上完全可以当作模块库动态加载，只是 `MODULE` 是 CMake 为“纯动态加载场景”提供的更精确的类型选择。
