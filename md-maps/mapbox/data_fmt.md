# 0..mbtiles 和  .pmtiles 分别是什么
<!-- googleAI -->
这两个都是目前 GIS 行业中最主流的地图瓦片打包存储格式，它们的核心目的都是把成百上千多万张零碎的地图小图片（或矢量 PBF 文件夹）打包成一个单文件，方便传输、管理和部署。
但它们的技术架构和适用场景有很大区别，可以用“上一代标准”与“下一代进化版”来形容：
------------------------------
## 📦 1. .mbtiles —— 经典的 SQLite 数据库包
.mbtiles 是由著名的地图公司 Mapbox 早期主导并开源的规范。

* 底层本质：它本质上是一个 SQLite 3 数据库文件。
* 工作原理：在这个数据库里，主要有两张表：一张存元数据（名称、范围、层级），另一张存瓦片数据。每一行就是一个瓦片，包含 zoom_level（层级）、tile_column（列）、tile_row（行）以及对应的 tile_data（二进制的图片或矢量数据）。
* 优点：
* 极为普及：几乎所有主流 GIS 工具（QGIS、ArcGIS、Tilemill 等）和开源服务器（如前面提到的 mbtileserver、martin）都原生支持它。
   * 支持修改：因为是数据库，你可以随时对里面某几张特定地点的瓦片进行更新、插入或删除。
* 缺点：
* 必须部署服务器：前端浏览器（如 Leaflet Pro）无法直接读取 .mbtiles 文件，必须在后端部署一个像 mbtileserver 这样的中间件，把数据库里的数据读取并转换成 HTTP URL（如 /z/x/y.png）才能给前端看。
   * 不适合云存储：由于它是 SQLite 数据库，无法直接放在 AWS S3 或阿里云 OSS 上通过普通的 HTTP 请求去查询其中某一个字节（并发高了数据库文件容易锁死或极慢）。

------------------------------
## ☁️ 2. .pmtiles —— 专为云原生诞生的下一代单文件格式
.pmtiles（Protomaps Tiles）是由 Protomaps 组织提出的一种云原生（Cloud-Native）瓦片归档格式，是近几年的 GIS 新宠。

* 底层本质：它是一个精心设计过的、纯二进制的静态文件（类似于云原生遥感格式 COG ）。
* 工作原理：它把地图的索引目录（Directory）全部放在文件的前端或特定位置。它最神奇的地方在于利用了 HTTP 协议的 Range Requests（范围请求） 特性。前端或服务器不需要下载整个几十 GB 的文件，只需要发送一个请求说：“请把这个文件中第 500 到 600 字节的内容给我”，就能直接精准拿到那一张瓦片。
* 优点：
* 无需后端服务器（Serverless）：你可以把一个 100GB 的 .pmtiles 文件直接扔进 AWS S3、阿里云 OSS 或 Cloudflare R2 等静态对象存储中。前端写几行 JS 代码（配合专用插件），浏览器就能直接去 S3 里“抠”出对应的瓦片进行渲染。你不需要为地图瓦片购买和维护任何运行代码的服务器，成本几乎降到零。
   * 极易 CDN 加速：由于每一次瓦片请求都变成了对静态文件特定区段的常规 HTTP 请求，CDN（如 Cloudflare）可以完美缓存这些区段，并发能力达到恐怖的工业级上限。
* 缺点：
* 无法轻易修改：它是只读的优化二进制结构。如果你的地图数据变了，你不能像数据库那样只更新其中一行，通常需要重新整体打包生成一个新的 .pmtiles 文件。

------------------------------
## ⚔️ 对比总结

| 特性 | .mbtiles (SQLite) | .pmtiles (Cloud-Native) |
|---|---|---|
| 文件本质 | 本地关系型数据库 | 顺序排列的二进制单文件 |
| 核心发布方式 | 必须通过后端服务器（如 mbtileserver） | 直接放对象存储（S3/OSS），或通过轻量代理（如 martin） |
| 服务器成本 | 💰 需要为服务器 CPU 和内存买单 | 🪙 几乎为零（只付存储和流量费） |
| 数据更新 | 支持增量动态更新 | 必须全量重新打包 |
| 适用场景 | 本地离线 GIS 软件、内网服务器部署、需要频繁微调数据的项目 | 公网大规模地图分发、省钱的 Serverless 架构、全国/全球基础底图 |

如果你现在要搭建一套面向公网的大地图服务，且底图数据（如全中国底图）几个月才变一次，强烈建议研究 .pmtiles + 对象存储 的方案（可以用 martin 作为其中间件代理，或直接纯前端加载），能帮你省下大笔的服务器费用。
你手头目前的地图数据，是更倾向于经常更新，还是做好了就不怎么变的静态底图呢？

# 1.生成多个 .pmtiles  放到静态对象存储中,是否可以满足增量动态更新

<!-- googleAI -->
是的，完全可以满足，但需要采用“图层分离”或“时间维/空间维分块”的架构设计。
由于 .pmtiles 本质上是只读的静态文件，你无法像传统数据库那样去修改文件内部的某几行数据。但是，通过把数据拆分成多个独立的 .pmtiles 文件并放置在对象存储（S3/OSS）中，配合前端地图框架（如 MapLibre GL JS）的动态叠加能力，可以非常完美、优雅地实现增量动态更新。
以下是工业界最常用的三种核心设计方案：
------------------------------
## 🎨 方案一：业务图层分离法（最推荐，解决“属性/业务变动”）
把地图数据按照“更新频率”拆分成不同的独立文件。

* 基础底图层（Base.pmtiles）：包含路网、水系、绿地等。数据量极大（几十 GB 到数 TB），但几个月甚至一年才变一次。永远不用动它。
* 增量业务层（Business.pmtiles 或 Dynamic.pmtiles）：只包含你的业务数据（例如：外卖配送范围、实时店铺位置、每日巡检轨迹）。数据量通常很小（几 MB 到几百 MB），每天或每小时全量重写覆盖一次。
* 前端合并：在前端 MapLibre 中，同时加载这两个文件作为不同的 source，然后把它们叠在一起渲染。
* 优点：更新时只需要重新打包并上传几 MB 的业务层文件，耗时只需几秒钟，基础底图完全不受影响。

------------------------------
## 🗺️ 方案二：空间网格分块法（解决“大范围、局部地理变动”）
如果你的基础底图本身也需要局部更新（例如：全国省道更新、某个新落成小区的建筑轮廓入库），你可以把全国按照省份或标准地理网格（Grid）拆分成多个文件。

* 目录结构：

my-bucket/
  ├── tiles/
  │    ├── guangdong.pmtiles  (广东)
  │    ├── beijing.pmtiles    (北京)
  │    └── shanghai.pmtiles   (上海 - 发生变动)

* 如何增量更新：如果上海的数据变了，你只需要在后台重新生成 shanghai.pmtiles 并直接上传覆盖对象存储中的旧文件。北京和广东的用户完全不受影响。
* 前端加载：前端可以通过判断当前用户视角的中心点（Center Bounding Box），动态去 addSource 加载对应省份的 .pmtiles。

------------------------------
## 🕒 方案三：时间序列切片法（解决“历史轨迹、时空回放”）
如果你的数据是随着时间源源不断产生的（例如：每小时的雷达气象图、每晚的共享单车停放热力图）。

* 目录结构：

my-bucket/
  ├── radar-20261025-1000.pmtiles
  ├── radar-20261025-1100.pmtiles
  └── radar-20261025-1200.pmtiles  (最新一小时的增量)

* 如何增量更新：后台定时任务每小时生成一个新的文件并丢进 S3。这是一种纯粹的追加（Append）式增量，绝对不会破坏历史数据。
* 前端加载：前端拉取文件列表，根据时间轴滑块，动态切换加载对应的 .pmtiles 文件。

------------------------------
## ⚠️ 纯静态对象存储架构下的注意事项
当你把多个 .pmtiles 放在对象存储中做增量更新时，需要特别注意以下两个“坑”：

   1. 浏览器缓存与 CDN 刷新（最核心问题）
   * 现象：你上传了新的 Business.pmtiles 覆盖了旧文件，但是用户打开网页发现地图还是老数据。
      * 原因：CDN（如 Cloudflare）或浏览器把旧文件的 HTTP Range 请求给缓存了。
      * 解决办法：
      * 方法 A（版本号法）：不要直接覆盖同名文件。每次更新生成带时间戳的文件（如 data_v20261025.pmtiles），前端通过后端接口获取最新的文件名去加载。
         * 方法 B（清除缓存）：如果必须同名覆盖，上传后必须调用 CDN 的 API 刷新该文件的缓存（Purge Cache）。
      2. 前端多数据源的样式管理（Style）
   * 如果你拆分了多个 .pmtiles，前端在写 Mapbox/MapLibre Style JSON 时，需要定义多个 sources。在增加或删除图层文件时，记得同步更新前端的样式解析逻辑。
   
## 💡 结论
这种“多个 .pmtiles + 对象存储”的方案完全可行。它用极低的成本（省去了长期开启高性能服务器的费用），通过前端多源融合的技术，完美绕开了静态文件“不易修改”的物理限制。

# 2. .pmtiles 文件 的流行,是不是martin\mbtileserver\Tegola等服务器就没有必要了
<!-- googleAI -->
不是的，.pmtiles 的流行并不会消灭这些服务器。
虽然 .pmtiles 的“无服务器（Serverless）”架构非常吸引人，但在实际的工业级 GIS 生产环境中，纯静态文件无法解决所有问题。martin、Tegola 等服务器依然拥有不可替代的核心价值。
它们之间不是“你死我活”的淘汰关系，而是“动静结合”的互补关系。以下是为什么在 .pmtiles 时代，这些瓦片服务器依然极其重要的原因：
------------------------------
## 1. 动态复杂查询与过滤（纯静态文件无法做到）

* 服务器的优势：像 martin 或 Tegola 连接 PostGIS 数据库时，前端可以发送带有动态参数的请求。例如：“只显示当前地块内面积大于500平米、且归属权属于A公司的建筑”。服务器会实时在数据库执行 SQL 过滤并瞬间生成瓦片。
* .pmtiles 的局限：它是已经“死”的数据。虽然前端拿到瓦片后可以用 JS 做一些简单的样式过滤，但如果底层数据量极大（例如几百万个要素），你无法在不下载完整数据的情况下，让静态文件只返回符合特定复杂 SQL 条件的瓦片。

## 2. 真正意义上的“实时（Real-time）”数据发布

* 服务器的优势：对于外卖小哥定位、报警事件、实时气象雷达、秒级更新的交通拥堵路段，pg_tileserv 或 martin 可以在数据发生变化的那一毫秒，直接从数据库读取并渲染成 MVT 返回给前端。
* .pmtiles 的局限：无论切片速度多快，.pmtiles 都需要一个“导出 -> 打包 -> 上传到 S3”的过程。即使数据每 5 分钟变一次，频繁打包成百上千兆的文件并上传，对 CPU 和网络带宽也是巨大的浪费。

## 3. 数据安全与细粒度权限控制（鉴权）

* 服务器的优势：在企业内部或敏感项目中，不同级别的用户看到的地图数据权限不同（例如：普通员工只能看普通道路，管理员能看内部管线）。瓦片服务器可以作为后端服务，在收到 HTTP 请求时检查用户的 Token/Cookie，决定是否返回该瓦片，或者在生成瓦片时动态剔除敏感字段。
* .pmtiles 的局限：虽然对象存储（S3/OSS）支持签名 URL，但它的权限控制是文件级别的。你很难做到“允许用户查看该 .pmtiles 文件的图层 A，但拒绝查看图层 B”，除非你为所有权限组合拆分出无数个独立的 .pmtiles 文件。

## 4. 事实上，主流服务器（如 martin）已经全面拥抱了 .pmtiles
这是一个非常有趣的演进：服务器和 .pmtiles 融合了。
最新的 martin 已经原生支持直接读取 .pmtiles 文件。在实际部署中，很多架构师会选择：
$$\text{【大文件 .pmtiles】} \rightarrow \text{【轻量级 martin 服务器】} \rightarrow \text{【安全鉴权/动态合并】} \rightarrow \text{【前端】}$$ 
这样做的好处是：

* 对内：本地硬盘不需要存放动辄几百 GB 的解压瓦片目录。
* 对外：统一了接口规范，加入了权限验证，并且可以把 .pmtiles 和 PostGIS 数据库的图层在服务器端直接动态融合成一个虚拟图层输出。

------------------------------
## ⚖️ 总结：它们未来的分工
在现代 GIS 架构中，它们的定位非常清晰：

| 业务需求场景 | 最终选型方案 |
|---|---|
| 公共大底图（OSM 卫星图、全国路网、不变的政区边界） | 🥇 直接用 .pmtiles + 对象存储（无需服务器，最省钱）。 |
| 企业高频更新业务（设备监控、每日业务报表、人员轨迹） | 🥇 选 martin / pg_tileserv + PostGIS（实时性无可替代）。 |
| 混合型混合架构（既需要大底图，又需要安全鉴权与多源合并） | 🥇 选 martin 作为代理 + 后端挂载 .pmtiles 与数据库。 |

因此，.pmtiles 革新的是大容量静态底图的分发分式，而 martin、Tegola 等服务器则继续在动态、实时、安全、复杂业务的阵地上发光发热。
你目前正在构思的项目，是否涉及到用户权限划分、或者极其高频（秒级/分钟级）的数据变动呢？

# 3 GeoPackage（`.gpkg`）
OGC国际标准，**基于SQLite单文件**，可以存原始矢量要素（点/线/面+属性）、栅格瓦片、元数据、空间R树索引。
> 重点区分：
> - **MBTiles：只存预切好的瓦片二进制（mvt/png）**；
> - **GeoPackage：优先存原始矢量要素表，不是预生成瓦片；瓦片是Tegola运行时实时裁切生成MVT**。

## 核心特性
1. OGC标准，QGIS、GDAL、ArcGIS全生态支持，替代shp（shapefile要一堆分散文件，gpkg单文件）。
2. 内部可以有多张要素表，自带R‑Tree空间索引，支持多坐标系，不限于3857墨卡托。
3. 可读写，可增删改要素；而mbtiles瓦片文件基本只读。
4. SQLite底层，所有SQLite工具都能打开查看内部表结构。

## 和Tegola的关系（非常关键）
Tegola支持`type="gpkg"`数据源，**读取gpkg里面原始矢量要素表，运行时根据z/x/y瓦片范围做空间查询，取出相交要素，裁切、简化、编码输出MVT瓦片**。

> ⚠️不是读取预切瓦片！
> 流程：http瓦片请求 → tegola查询gpkg(SQLite)要素表，按瓦片bbox做空间过滤 → 内存做几何处理 → 输出MVT。
> **不开启cache时，每一次瓦片http请求，都会查询gpkg这个sqlite数据库**，和PostGIS逻辑几乎一样，只是数据库是本地文件，不是网络PG库。

> 注意：tegola读取gpkg需要CGO，纯静态无cgo编译版本不支持gpkg provider。

### tegola gpkg最简配置片段
```toml
[[providers]]
name = "park_gpkg"
type = "gpkg"
filepath = "./park.gpkg"

[[providers.layers]]
name = "roads"
tablename = "roads"
geometry_fieldname = "geom"
id_fieldname = "fid"

[cache]
type = "file"
basepath = "./tegola_cache"
```
> 同样，必须配置`[cache]`，否则每次请求都查sqlite文件。

## GPKG vs MBTiles vs PMTiles（结合你的项目）
|格式|本质|内容|使用方式|适合工具|
|---|---|---|---|---|
|**GeoPackage(gpkg)**|SQLite数据库|**原始矢量要素（带属性）**|服务端实时裁切生成MVT|Tegola；QGIS；不适合mbtileserver/martin直接读瓦片|
|**MBTiles**|SQLite数据库|**预切好MVT瓦片blob**|直接读取已经切好的瓦片|mbtileserver、martin|
|**PMTiles**|单文件自定义索引|预切MVT瓦片blob|HTTP Range随机读，无SQL|Martin最优支持|

> 通俗理解：
> - gpkg：存放原始数据，相当于一个轻量本地版PostGIS；
> - mbtiles / pmtiles：存放已经切好的成品瓦片，直接返回给前端，不需要实时计算几何。

## 你的技术链路怎么选
### 场景A：原始数据，需要动态实时生成瓦片（比如要素会经常修改）
> shp → QGIS导出 **gpkg** → 交给Tegola做服务。
> 优点：修改gpkg里的要素，不需要重新跑tippecanoe/tilemaker重切瓦片；Tegola实时生成。
> 缺点：每次miss都要sqlite空间查询，CPU、IO开销更大；2核4G机器压力比读预切mbtiles更大。

### 场景B：静态数据，很少改动（园区底图，一次切图长期使用）
> shp → tilemaker/tippecanoe → **mbtiles / pmtiles** → mbtileserver / martin直接提供瓦片服务。
> 优点：服务端不需要几何计算，开销极低；2核4G很舒服。
> 缺点：数据改动，必须重新切图。

## 常见坑
1. **不要混淆：gpkg可以存瓦片，但tegola的gpkg provider读取的是要素表，不是瓦片表**。如果你把预切瓦片存进gpkg，tegola不会把它当做瓦片库来读。
2. gpkg的空间索引必须建好，否则瓦片查询巨慢。QGIS导出gpkg记得勾选创建空间索引。
3. gpkg是sqlite，并发读有锁问题；高并发场景性能弱于pmtiles。
4. 不要拿gpkg直接丢给mbtileserver，mbtileserver只识别mbtiles规范的表结构。

## 简短总结
- **gpkg = 文件版轻量级空间数据库，存原始矢量要素，用于Tegola动态生成瓦片**。
- **mbtiles/pmtiles = 成品瓦片包，直接返回瓦片，不需要实时几何运算，适合静态底图**。
> 你的园区项目，如果底图几乎不变，优先 tilemaker输出pmtiles/mbtiles，用martin/mbtileserver；如果需要频繁修改要素，用gpkg+Tegola并且务必开启cache。
