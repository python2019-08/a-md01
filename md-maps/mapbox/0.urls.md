# 1.Awesome implementations of the Mapbox Vector Tile specification

https://github.com/mapbox/awesome-vector-tiles

## 从awesome-vector-tiles提供的列表来看，以下几个服务是用 Go 语言（Golang） 编写的：

> go-vtile-example: 一个用 Go 语言编写的示例地图服务。
> mbtileserver: 一个简单的、基于 Go 语言的服务器，用于提供存储在 mbtiles 格式文件中的地图切片。
> Tegola: 一个用 Go 语言编写的矢量切片服务器，支持 PostGIS 和 GeoPackage 数据源（你在前面也刚了解过它）。
> pg_tileserv: 一个非常轻量级的、纯 PostGIS 的 Go 语言瓦片服务器，负责接收 HTTP 瓦片请求、执行 SQL 并返回 MVT 瓦片。
 

###  martin: 用 Rust编写
martin: 一个用 Rust 编写的高性能 PostGIS/MBtiles/PMtiles 切片服务器（注：虽然它是 Rust 写的，但值得单独注意，不过在你的问题里只找 Go 的即可）。(等下，Martin 是 Rust 写的)

### 性能对比

在这几个 Go 语言编写的服务端中，单论纯粹的高并发吞吐量和性能，表现最好的是 pg_tileserv，其次是 Tegola。

不过，我们可以从性能、设计以及生态横向对比来具体看它们的差异：

#### 1. 性能梯队对比（Go 语言阵营）
第一名：pg_tileserv
特点：它是专门为 PostGIS 量身定制的极简瓦片服务器。
为什么快：它的代码极其轻量，几乎不做多余的数据转换和复杂的中间处理，核心逻辑就是直接接收 HTTP 请求、安全地把请求转交给 PostGIS 数据库去跑 ST_AsMVT（数据库原生的高效二进制切片函数），然后直接把结果丢给客户端。由于减少了应用层的内存分配和复杂计算，它的吞吐量在 Go 语言实现的同类服务中非常高。

第二名：Tegola
特点：功能全面、成熟度高的老牌矢量切片服务器。
为什么稍逊一筹：Tegola 做了更多抽象层（支持多数据源切换、更复杂的配置、图层映射、缓存策略等）。这些抽象带来了更好的灵活性，但在极致的吞吐量压测下，应用层的额外开销会比 pg_tileserv 略高一点。

其他（mbtileserver, go-vtile-example）：
mbtileserver 只是单纯从本地的 .mbtiles 文件里读数据并吐出去，性能取决于磁盘 IO，通常作为特定静态场景使用。
go-vtile-example 仅为示例代码，不适合生产环境。

#### 2. 一个重要的行业现状提示 ⚠️
虽然 pg_tileserv 性能很好，但开源社区的动态值得注意：
pg_tileserv 的主要维护者（Paul Ramsey 大神）在近年已将其标记为不再活跃维护（no longer actively maintained）。
当前在整个开源 GIS 社区中（包括上面那份列表中没被选入 Go 语言的 Martin（用 Rust 写的）），性能与生态风头最劲的是 Martin。在权威的公开基准测试（如 Spatialists 的评测）中，用 Rust 写的 Martin 凭借非阻塞请求和极致的内存优化，把包括 Go 语言在内的很多同类对手甩开了数倍的差距。

#### 3.  选型建议
如果你受限于技术栈必须用 Go 语言：
且后端数据库是纯正的 PostgreSQL/PostGIS，追求极致轻量和高性能，首选 pg_tileserv。
如果你需要更复杂的图层管理、多数据源支持以及较好的扩展性，选 Tegola。

如果你对语言没有硬性要求，追求当下的绝对性能天花板：
建议直接考虑**用 Rust 写的 Martin**（它同样完美支持 PostGIS、MBTiles、PMTiles，是目前行业内公认最快的动态切片服务器之一）。https://github.com/maplibre/martin
