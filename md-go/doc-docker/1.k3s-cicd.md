# 1.k3s   jenkins golang cicd

在 Ubuntu 单机 i9 环境下，结合 K3s、Jenkins 和 Golang 搭建 CI/CD 流水线是非常高效的组合，尤其适合个人开发者或小型团队进行容器化应用的开发、测试与部署。以下是具体方案和实施思路：


### **一、组合优势分析**
1. **K3s 的轻量与适配性**  
   K3s 作为轻量版 Kubernetes，在单机 i9 上资源占用低（默认仅占用 ~512MB 内存），部署简单（一键安装），且兼容 Kubernetes 核心 API，可直接使用 `kubectl` 管理，适合本地开发环境模拟集群部署。  
   相比 K8s，K3s 省去了复杂的组件配置（如独立 etcd 集群），内置 SQLite 作为默认存储，更适合单机场景。

2. **Jenkins 的自动化能力**  
   Jenkins 作为成熟的 CI/CD 工具，可通过插件（如 `Kubernetes Plugin`）与 K3s 集成，实现：  
   - 代码拉取（Git）→ 编译构建（Golang）→ 镜像打包（Docker）→ 推送到镜像仓库  
   - 自动部署到 K3s 集群，并进行滚动更新或回滚  

3. **Golang 的容器化适配**  
   Golang 编译产物为静态二进制文件，体积小、依赖少，非常适合容器化打包。结合多阶段构建（`multi-stage build`），可进一步减小镜像体积，提升部署效率。


### **二、搭建步骤**

#### **1. 安装 K3s（单机模式）**
在 Ubuntu 上一键安装 K3s（默认包含 `kubectl`）：  
```bash
# 安装 K3s（禁用 traefik 可选，避免与自定义 ingress 冲突）
curl -sfL https://get.k3s.io | sh -s - --disable=traefik

# 验证安装（查看节点状态）
sudo kubectl get nodes
# 输出应为 Ready 状态
```
- 配置文件路径：`/etc/rancher/k3s/k3s.yaml`（集群访问配置）
- 如需外部访问，可复制该文件到 `~/.kube/config` 并修改 IP。


#### **2. 安装 Jenkins（部署到 K3s 或本地）**
##### **方案一：部署到 K3s 集群（推荐，容器化管理）**
见：《# 2.jenkins-deploy.yaml放置到什么地方》
创建 Jenkins 部署清单（`jenkins-deploy.yaml`）：  
```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: jenkins
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: jenkins
  namespace: jenkins
spec:
  replicas: 1
  selector:
    matchLabels:
      app: jenkins
  template:
    metadata:
      labels:
        app: jenkins
    spec:
      containers:
      - name: jenkins
        image: jenkins/jenkins:lts-jdk17  # 适配 Golang 1.18+ 推荐 JDK17
        ports:
        - containerPort: 8080
        - containerPort: 50000
        volumeMounts:
        - name: jenkins-home
          mountPath: /var/jenkins_home
        - name: docker-sock  # 挂载宿主机 Docker 套接字（用于构建镜像）
          mountPath: /var/run/docker.sock
      volumes:
      - name: jenkins-home
        persistentVolumeClaim:
          claimName: jenkins-pvc
      - name: docker-sock
        hostPath:
          path: /var/run/docker.sock
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: jenkins-pvc
  namespace: jenkins
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi  # 根据需求调整
---
apiVersion: v1
kind: Service
metadata:
  name: jenkins
  namespace: jenkins
spec:
  selector:
    app: jenkins
  ports:
  - port: 80
    targetPort: 8080
  type: NodePort  # 单机可使用 NodePort 暴露端口
```

部署到 K3s：  
```bash
sudo kubectl apply -f jenkins-deploy.yaml

# 查看 Jenkins 服务端口（例如 NodePort 为 30080）
sudo kubectl get svc -n jenkins
```

访问 Jenkins：`http://localhost:30080`，初始密码获取：  
```bash
# 进入 Jenkins 容器
# 见 《# 3.<jenkins-pod-name>》
sudo kubectl exec -it -n jenkins <jenkins-pod-name> -- cat /var/jenkins_home/secrets/initialAdminPassword
```


##### **方案二：本地安装 Jenkins（适合更灵活的环境配置）**
```bash
# 安装 Java（Jenkins 依赖）
sudo apt update && sudo apt install openjdk-17-jdk -y

# 安装 Jenkins
curl -fsSL https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key | sudo tee /usr/share/keyrings/jenkins-keyring.asc > /dev/null
echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" | sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt update && sudo apt install jenkins -y

# 启动并设置开机自启
sudo systemctl start jenkins && sudo systemctl enable jenkins
```


#### **3. 配置 Jenkins 与 Golang 环境**
1. **安装必要插件**  
   进入 Jenkins 控制台 → **Manage Jenkins** → **Plugins**，安装：  
   - `Git Plugin`（拉取代码）  
   - `Pipeline`（流水线支持）  
   - `Kubernetes Plugin`（与 K3s 集成，可选）  
   - `Docker Plugin`（构建镜像）  
   - `Golang Plugin`（配置 Golang 环境）  

2. **配置 Golang 环境**  
   - 进入 **Manage Jenkins** → **Global Tool Configuration** → **Golang**  
   - 点击 **Add Golang**，选择版本（如 1.21），勾选“自动安装”，保存。  


#### **4. 编写 Golang 项目 CI/CD 流水线（Jenkinsfile）**
假设项目结构如下：  
```
golang-demo/
├── main.go         # 示例代码（简单 HTTP 服务）
├── Dockerfile      # 容器化配置
└── Jenkinsfile     # CI/CD 流水线定义
```

##### **示例代码（main.go）**
```go
package main

import (
  "fmt"
  "net/http"
)

func main() {
  http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintf(w, "Hello, K3s + Jenkins + Golang!")
  })
  http.ListenAndServe(":8080", nil)
}
```

##### **Dockerfile（多阶段构建）**
```dockerfile
# 第一阶段：编译 Golang 二进制文件
FROM golang:1.21-alpine AS builder
WORKDIR /app
COPY . .
RUN go mod init demo && go build -o app main.go

# 第二阶段：生成轻量镜像
FROM alpine:3.18
WORKDIR /app
COPY --from=builder /app/app .
EXPOSE 8080
CMD ["./app"]
```

##### **Jenkinsfile（流水线脚本）**
```groovy
pipeline {
  agent any  # 若使用 K3s 动态代理，可配置为 kubernetes 代理

  tools {
    go '1.21'  # 对应 Global Tool Configuration 中配置的 Golang 名称
  }

  stages {
    stage('拉取代码') {
      steps {
        git url: 'https://github.com/your-repo/golang-demo.git', branch: 'main'
      }
    }

    stage('编译构建') {
      steps {
        sh 'go mod tidy'
        sh 'go build -o app main.go'  # 本地编译验证
      }
    }

    stage('构建并推送镜像') {
      steps {
        sh '''
          # 构建镜像（标签包含 commit ID）
          IMAGE_TAG=$(git rev-parse --short HEAD)
          docker build -t golang-demo:$IMAGE_TAG .

          # 如需推送到仓库（如 Docker Hub），需先登录
          # docker login -u username -p password
          # docker tag golang-demo:$IMAGE_TAG username/golang-demo:$IMAGE_TAG
          # docker push username/golang-demo:$IMAGE_TAG
        '''
      }
    }

    stage('部署到 K3s') {
      steps {
        sh '''
          # 使用 kubectl 部署到 K3s（确保 Jenkins 有权限访问 K3s 配置）
          # 若 Jenkins 部署在 K3s 内，可直接使用集群内配置
          kubectl apply -f k8s/deployment.yaml  # 假设部署清单在项目 k8s 目录下
        '''
      }
    }
  }

  post {
    success {
      echo 'CI/CD 流水线执行成功！'
    }
    failure {
      echo '流水线执行失败，请检查日志。'
    }
  }
}
```


#### **5. 部署到 K3s 的配置（deployment.yaml）**
在项目中创建 `k8s/deployment.yaml`，定义应用部署：  
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: golang-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: golang-demo
  template:
    metadata:
      labels:
        app: golang-demo
    spec:
      containers:
      - name: golang-demo
        image: golang-demo:$(IMAGE_TAG)  # 镜像标签与流水线中一致
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: golang-demo
spec:
  selector:
    app: golang-demo
  ports:
  - port: 80
    targetPort: 8080
  type: NodePort
```


### **三、关键注意事项**
1. **权限问题**  
   - Jenkins 需拥有访问 K3s 的权限（若部署在集群外，需将 `k3s.yaml` 配置到 Jenkins 节点的 `~/.kube/config`）。  
   - 若使用 Docker 构建镜像，Jenkins 用户需加入 `docker` 组：`sudo usermod -aG docker jenkins`。

2. **资源优化**  
   i9 处理器性能充足，但可通过 K3s 的资源限制（`resources.limits`）避免单个 Pod 占用过多资源。

3. **镜像仓库选择**  
   本地测试可使用 `k3d` 搭建私有 registry，或直接使用 Docker Hub 公共仓库。


### **总结**
单机 i9 + Ubuntu 环境下，**K3s + Jenkins + Golang** 是轻量且高效的组合：  
- K3s 提供简化的 Kubernetes 体验，适合本地开发；  
- Jenkins 负责自动化流水线，整合代码构建、镜像打包与部署；  
- Golang 的轻量特性与容器化完美适配，整个流程流畅高效。  

按上述步骤操作，可快速搭建一套完整的本地 CI/CD 环境，适合个人或小团队验证容器化应用的开发与部署流程。

# 2.jenkins-deploy.yaml放置到什么地方

在 Kubernetes（或 K3s）环境中，`jenkins-deploy.yaml` 这类用于部署 Jenkins 的 YAML 配置文件的**存放位置没有强制的固定要求**，但通常需要遵循一定的管理习惯，以便于操作和维护。以下是常见的存放方式和建议：

  

## 2.1. 关键原则
- **核心是“能被 kubectl 访问到”**：只要执行 `kubectl apply -f <文件路径>` 时，`kubectl` 能读取到该 YAML 文件即可（本地路径、网络路径均可，例如 `kubectl apply -f https://example.com/jenkins-deploy.yaml`）。
- **便于管理和追溯**：优先选择本地工作目录 + Git 版本控制的方式，避免随意存放导致文件丢失或配置混乱。
- **Kubernetes 集群内（不推荐直接存放）**
   - Kubernetes 本身不提供专门的“配置文件存储目录”，集群内的资源（如 Deployment、Service 等）是通过 API 服务器管理的，而非直接读取节点上的文件。
   - 若需在集群内临时使用该文件（例如在控制节点上操作），可存放于任意目录（如 `/tmp/` 或 `/root/manifests/`），但重启后可能丢失，**不适合长期管理**。

部署后，Kubernetes 会将 YAML 中定义的资源（如 Jenkins 的 Deployment、Service 等）存储在集群的 etcd 数据库中，后续修改只需更新 YAML 文件并重新执行 `kubectl apply` 即可。

## 2.2. 本地工作目录 + Git 版本控制*
采用**本地工作目录 + Git 版本控制**管理 Jenkins 部署配置（如 `jenkins-deploy.yaml`）的流程如下，以 Ubuntu 系统为例：


### **1. 创建本地工作目录**
```bash
# 创建项目根目录（例如名为 k8s-configs）
mkdir -p ~/k8s-configs/jenkins
cd ~/k8s-configs/jenkins

# 创建 Jenkins 相关配置文件（或从已有文件复制）
touch jenkins-deploy.yaml  # 编辑该文件，填入 Jenkins 部署配置
```


### **2. 初始化 Git 仓库**
```bash
# 在项目根目录初始化 Git 仓库
cd ~/k8s-configs
git init

# 添加 .gitignore 文件（可选，排除不必要的文件）
echo "*.log" > .gitignore
echo "*.bak" >> .gitignore
```


### **3. 将配置文件添加到 Git 管理**
```bash
# 添加文件到暂存区
git add jenkins/  # 添加 jenkins 目录下的所有文件

# 提交到本地仓库
git commit -m "初始提交：Jenkins 部署配置"
```


### **4. 关联远程仓库（如 GitHub/GitLab）**
```bash
# 在 GitHub 或 GitLab 上创建空仓库（例如名为 k8s-configs）
# 关联远程仓库
git remote add origin https://github.com/your-username/k8s-configs.git

# 推送本地代码到远程仓库
git push -u origin main  # 首次推送需指定上游分支
```


### **5. 团队协作与版本控制**
- **其他成员拉取代码**：
  ```bash
  git clone https://github.com/your-username/k8s-configs.git
  ```

- **修改配置后提交**：
  ```bash
  # 修改 jenkins-deploy.yaml 后
  git add jenkins/jenkins-deploy.yaml
  git commit -m "更新 Jenkins 内存限制"
  git push origin main
  ```


### **6. 使用配置文件部署到 K3s**
```bash
# 从本地工作目录部署
kubectl apply -f ~/k8s-configs/jenkins/jenkins-deploy.yaml

# 或从远程仓库直接部署（适合 CI/CD 自动化）
kubectl apply -f https://raw.githubusercontent.com/your-username/k8s-configs/main/jenkins/jenkins-deploy.yaml
```


### **7. 最佳实践建议**
1. **目录结构组织**：
   ```
   k8s-configs/
   ├── jenkins/
   │   ├── jenkins-deploy.yaml       # Jenkins 部署
   │   ├── jenkins-service.yaml      # Jenkins 服务暴露
   │   └── jenkins-ingress.yaml      # 可选：Ingress 配置
   ├── monitoring/                   # 其他组件（如监控）
   └── README.md                     # 项目说明
   ```

2. **分支管理**：
   - 使用 `main` 分支存放稳定版本的配置。
   - 开发新功能或修改配置时，创建新分支（如 `feature/jenkins-upgrade`），测试通过后合并到 `main`。

3. **配置版本化**：
   - 在 YAML 文件中添加注释说明配置用途和变更历史。
   - 使用标签（Tags）标记重要版本（如 `v1.0.0`）。


### **优势总结**
- **可追溯性**：通过 Git 记录每次配置变更，便于回滚和审计。
- **团队协作**：多人可同时维护配置，避免冲突。
- **自动化部署**：CI/CD 工具（如 Jenkins）可直接从 Git 仓库拉取最新配置进行部署。
- **环境隔离**：不同环境（开发/测试/生产）可使用不同分支或目录管理配置。

通过这种方式，你可以高效管理 Jenkins 部署配置，同时享受版本控制带来的便利。

# 3.<jenkins-pod-name>

```sh
sudo kubectl exec -it -n jenkins <jenkins-pod-name> -- cat /var/jenkins_home/secrets/initialAdminPassword
```
这里<jenkins-pod-name>如何填写

在执行 `sudo kubectl exec -it -n jenkins <jenkins-pod-name> -- cat /var/jenkins_home/secrets/initialAdminPassword` 命令时，`<jenkins-pod-name>` 需要替换为实际运行的 Jenkins Pod 的名称。以下是获取和填写该名称的具体步骤：


### **1. 查询 Jenkins Pod 的名称**
使用以下命令查看 `jenkins` 命名空间下的所有 Pod：
```bash
sudo kubectl get pods -n jenkins
```

**示例输出**：
```
NAME                        READY   STATUS    RESTARTS   AGE
jenkins-7f56c8989f-8z2bk   1/1     Running   0          3m
```
这里的 `jenkins-7f56c8989f-8z2bk` 就是 Jenkins Pod 的实际名称。


### **2. 替换命令中的占位符**
将获取到的 Pod 名称填入命令中：
```bash
# 示例（根据实际输出替换 Pod 名称）
sudo kubectl exec -it -n jenkins jenkins-7f56c8989f-8z2bk -- cat /var/jenkins_home/secrets/initialAdminPassword
```


### **3. 简化操作的技巧**
#### **方法一：使用 `$(...)` 自动获取 Pod 名称**
如果只有一个 Jenkins Pod，可以通过命令自动获取名称，避免手动复制：
```bash
sudo kubectl exec -it -n jenkins $(sudo kubectl get pods -n jenkins -o name | grep jenkins) -- cat /var/jenkins_home/secrets/initialAdminPassword
```

#### **方法二：使用 `--field-selector` 过滤**
如果 Pod 名称规律明显，可以通过标签过滤：
```bash
# 假设 Jenkins Pod 有 app=jenkins 标签
sudo kubectl exec -it -n jenkins $(sudo kubectl get pods -n jenkins -l app=jenkins -o name) -- cat /var/jenkins_home/secrets/initialAdminPassword
```


### **4. 验证 Pod 状态**
在执行命令前，确保 Pod 处于 `Running` 状态（`STATUS` 列显示 `Running`）。如果 Pod 处于 `Pending`、`Error` 或 `CrashLoopBackOff` 状态，需要先排查问题（如查看日志：`sudo kubectl logs -n jenkins <pod-name>`）。


### **最终效果**
执行正确的命令后，会输出 Jenkins 的初始管理员密码（一串随机字符），用于首次登录 Jenkins 控制台。例如：
```
7e2b5c7a1f3d4b9c8e7a2d5f6e9a0b
```


### **注意事项**
- 如果 Jenkins 部署使用了 StatefulSet（而非 Deployment），Pod 名称可能为 `jenkins-0` 这种格式。
- 若 Pod 名称包含特殊字符（如 `.`、`_`），需原样保留，无需转义。

# 4.浏览器里打不开 """"localhost:30080""""

执行了sudo kubectl exec -it -n jenkins <jenkins-pod-name> -- cat /var/jenkins_home/secrets/initialAdminPassword ，但是在浏览器里打不开 """"localhost:30080""""

在浏览器中无法访问 `localhost:30080`（Jenkins 页面），通常是由于 **Jenkins 服务未正确暴露端口** 或 **Pod/服务状态异常** 导致的。以下是详细排查步骤：


### **1. 确认 Jenkins Pod 状态**
首先确保 Jenkins Pod 处于正常运行状态：
```bash
sudo kubectl get pods -n jenkins
```
**正常输出** 应显示 `STATUS` 为 `Running`，`READY` 为 `1/1`（示例）：
```
NAME                        READY   STATUS    RESTARTS   AGE
jenkins-7f56c8989f-8z2bk   1/1     Running   0          10m
```
- 如果状态为 `Pending`：可能是资源不足（CPU/内存不够），可通过 `sudo kubectl describe pod <pod-name> -n jenkins` 查看具体原因。
- 如果状态为 `CrashLoopBackOff`：Pod 启动失败，需查看日志：`sudo kubectl logs <pod-name> -n jenkins`。


### **2. 检查 Jenkins 服务（Service）配置**
Jenkins 的端口访问依赖于 Kubernetes 的 **Service 配置**（通常是 `jenkins-service.yaml`）。需确认 Service 正确暴露了端口，并映射到 Pod 的 8080 端口（Jenkins 默认端口）。

#### **查看 Service 配置**
```bash
sudo kubectl get svc -n jenkins
```
**正常输出** 应类似：
```
NAME         TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)          AGE
jenkins      NodePort   10.43.123.45    <none>        8080:30080/TCP   10m
```
- 关键信息：`PORT(S)` 需显示 `8080:30080/TCP`，其中 `30080` 是 NodePort（即你访问的 `30080` 端口）。
- 如果 `TYPE` 不是 `NodePort`（例如是 `ClusterIP`），则无法通过 `localhost:端口` 访问，需修改 Service 为 `NodePort` 类型。


### **3. 修复 Service 配置（若端口未暴露）**
如果 Service 未配置 `NodePort`，需修改其 YAML 配置（例如 `jenkins-service.yaml`）：
```yaml
apiVersion: v1
kind: Service
metadata:
  name: jenkins
  namespace: jenkins
spec:
  selector:
    app: jenkins  # 需与 Pod 的标签一致
  type: NodePort  # 关键：指定为 NodePort 类型
  ports:
  - port: 8080          # Service 内部端口（对应 Pod 的 8080 端口）
    targetPort: 8080    # Pod 暴露的端口（Jenkins 默认监听 8080）
    nodePort: 30080     # 宿主机端口（范围：30000-32767）
```
应用配置：
```bash
sudo kubectl apply -f jenkins-service.yaml -n jenkins
```


### **4. 检查宿主机端口映射**
如果 Service 配置正确，但仍无法访问，需确认 `30080` 端口已在宿主机上开放：
```bash
# 查看端口是否被监听
sudo netstat -tulpn | grep 30080
```
**正常输出** 应显示类似：
```
tcp6       0      0 :::30080                :::*                    LISTEN      1234/kube-proxy
```
- 若未显示，可能是 `kube-proxy` 未正常工作，重启 K3s 服务：
  ```bash
  sudo systemctl restart k3s
  ```


### **5. 确认访问地址是否正确**
- **本地机器部署 K3s**：直接使用 `localhost:30080` 访问。
- **远程服务器部署 K3s**：需用服务器的 **IP 地址** 替代 `localhost`，例如 `192.168.1.100:30080`（确保防火墙开放 `30080` 端口）。
- **虚拟机/容器环境**：若在虚拟机（如 VirtualBox）或 WSL2 中部署，需确认网络模式为 **桥接模式** 或 **端口转发已配置**。


### **6. 检查 Jenkins 容器日志**
如果以上步骤均正常，可能是 Jenkins 服务未在容器内正常启动：
```bash
sudo kubectl logs <jenkins-pod-name> -n jenkins
```
查看日志中是否有错误信息，例如：
- `Failed to initialize Jenkins`：配置文件损坏，需删除存储卷重新部署。
- `Address already in use`：端口冲突，检查 Pod 内是否有其他进程占用 8080 端口。


### **7. 临时端口转发（快速验证）**
如果 NodePort 配置有问题，可通过 `kubectl port-forward` 临时暴露端口验证：
```bash
# 将本地 8080 端口转发到 Pod 的 8080 端口
sudo kubectl port-forward -n jenkins <jenkins-pod-name> 8080:8080
```
此时在浏览器访问 `localhost:8080`，若能打开 Jenkins 页面，则说明问题出在 **Service 配置** 或 **NodePort 端口占用**。


### **总结**
核心问题通常是 **Service 未正确配置 NodePort** 或 **Pod 未正常启动**。按以下优先级排查：
1. 确认 Pod 状态为 `Running`。
2. 检查 Service 类型为 `NodePort` 且 `nodePort: 30080`。
3. 验证宿主机 `30080` 端口是否被监听。
4. 使用正确的访问地址（本地 `localhost` 或远程服务器 IP）。

解决后，刷新浏览器访问 `localhost:30080`，即可看到 Jenkins 登录页面，输入之前获取的 `initialAdminPassword` 完成初始化。

在 Jenkins 中找不到 **Kubernetes Plugin**（也称为 **CloudBees Kubernetes Continuous Deploy Plugin**）通常是由于插件名称变更、版本兼容性问题或仓库配置错误导致的。以下是详细的解决方案：


### **1. 确认正确的插件名称**

#### **核心插件列表**
| **插件名称**                          | **功能描述**                                                                 |
|---------------------------------------|----------------------------------------------------------------------------|
| **Kubernetes Plugin**                | 最常用的插件，允许 Jenkins 动态创建 Pod 作为构建代理（Agent），与 K3s/K8s 集群集成。 |

1. 进入 Jenkins 管理界面：

1. 进入 **Manage Jenkins** → **Manage Plugins** → **Advanced**（高级）。

2. 确认 **Update Site** 为官方地址：  
   `https://updates.jenkins.io/update-center.json`

3. 点击 **Check now**（立即检查）更新插件索引。

4. 再次尝试搜索 **Kubernetes Plugin**。


### **4. 检查 Jenkins 版本兼容性**
确保你的 Jenkins 版本支持该插件：
- **Jenkins 2.303+**：推荐使用最新版 Kubernetes Plugin（通常兼容）。
- **较旧的 Jenkins 版本**：可能需要安装兼容的插件版本（在插件详情页选择历史版本）。


### **5. 备选方案：使用 Pipeline 脚本直接集成**
如果插件安装失败，可通过 Jenkins Pipeline 脚本直接调用 `kubectl` 命令与 K3s 交互：

1. 在 Jenkins 节点上安装 `kubectl` 工具。

2. 使用以下 Pipeline 脚本示例：
```groovy
pipeline {
    agent any
    
    stages {
        stage('Deploy to K3s') {
            steps {
                // 使用已配置的 kubeconfig 文件
                sh 'kubectl --kubeconfig=/path/to/k3s.yaml apply -f deployment.yaml'
                
                // 或使用环境变量指定 kubeconfig
                sh 'KUBECONFIG=/path/to/k3s.yaml kubectl apply -f service.yaml'
            }
        }
    }
}
```


### **6. 验证插件安装成功**
安装后，在 Jenkins 系统配置中应看到 **Cloud** 部分新增了 **Kubernetes** 选项：
1. 进入 **Manage Jenkins** → **Configure System**（系统配置）。
2. 滚动到 **Cloud** 部分，点击 **Add a new cloud** → **Kubernetes**：  
   ![Kubernetes 配置项](https://i.imgur.com/5p5p5p5.png)


### **常见问题排查**
- **网络问题**：确保 Jenkins 服务器能访问外网（尤其是 `updates.jenkins.io`）。
- **权限问题**：确认 Jenkins 进程有足够权限安装插件。
- **插件冲突**：卸载其他 Kubernetes 相关插件（如 `Kubernetes Continuous Deploy`）后重试。

如果问题仍然存在，可提供 Jenkins 版本和错误日志，进一步排查。

在k3s环境的Jenkins中安装Kubernetes Plugin时出现`sun.security.provider.certpath.SunCertPathBuilderException`错误，核心原因是**Jenkins进程无法验证目标HTTPS服务器（如插件下载地址）的SSL证书**，通常与证书未被信任、网络代理或镜像源配置有关。以下是针对性的解决方法：


### **一、错误本质分析**
Jenkins安装插件时会从官方源（如`https://updates.jenkins.io`）或镜像源（如清华镜像`https://mirrors.tuna.tsinghua.edu.cn/jenkins`）下载文件。若服务器使用的SSL证书未被Jenkins所在JVM的信任库（`cacerts`）识别，就会触发SSL握手失败。

在k3s环境中，Jenkins通常以容器化方式运行，问题可能出在：
- 容器内JVM未信任目标证书；
- 网络代理拦截了HTTPS请求（如企业内网代理），导致证书被替换；
- 镜像源配置的URL使用了自签名证书或无效证书。


### **二、解决方法**

#### **方法1：更换Jenkins插件源为HTTP协议（临时应急）**
若环境允许使用HTTP（非生产环境慎用），可临时绕过SSL验证：
1. 进入Jenkins管理界面 → **Manage Jenkins** → **Plugin Manager** → **Advanced**。
2. 在“Update Site”中，将默认的`https://updates.jenkins.io/update-center.json`替换为HTTP源（如清华HTTP镜像）：  
   `http://mirrors.tuna.tsinghua.edu.cn/jenkins/updates/update-center.json`。
3. 点击“Submit”保存，重启Jenkins后重试安装。


#### **方法2：导入证书到Jenkins容器的JVM信任库（推荐）**
若必须使用HTTPS，需将目标服务器的SSL证书导入Jenkins容器内JVM的`cacerts`信任库。

##### **步骤1：获取目标服务器的SSL证书**
以清华镜像源`https://mirrors.tuna.tsinghua.edu.cn`为例：
```bash
# 在k3s节点或能访问该URL的机器上执行，导出证书到文件
echo -n | openssl s_client -connect mirrors.tuna.tsinghua.edu.cn:443 | sed -ne '/-BEGIN CERTIFICATE-/,/-END CERTIFICATE-/p' > tsinghua.crt
```

# 8.通过浏览器访问https站点并导出证书

不同浏览器导出HTTPS证书的方法略有差异，以下是Chrome、Firefox和Edge浏览器的具体操作步骤：
- **Google Chrome**：
    - 打开Chrome浏览器，访问需要导出证书的HTTPS网站。
    - 点击地址栏左侧的锁形图标，在弹出的菜单中点击“证书”按钮。
    - 进入证书详情页面后，点击“导出”按钮。
    - 根据提示选择证书格式，如DER编码、PEM格式（.crt）等，再选择存储位置并命名证书文件，最后点击“完成”即可。
- **Mozilla Firefox**：
    - 用Firefox浏览器打开目标HTTPS网站。
    - 点击地址栏旁边的锁图标，选择“证书”选项。
    - 在证书管理器中，找到目标网站的证书，右键点击该证书，选择“导出”。
    - 按照向导提示，选择证书格式（如P12、DER等）和存储位置，可按需设置密码，完成证书导出。
- **Microsoft Edge**：
    - 访问要导出证书的HTTPS站点。
    - 点击地址栏左侧的安全图标（通常是一个锁），选择“证书”。
    - 在证书窗口中，切换到“详细信息”选项卡，然后点击“复制到文件”。
    - 依据证书导出向导，选择合适的格式和保存路径，输入文件名，点击“下一步”并完成导出操作。

## 从浏览器导出的证书是pem格式，如何转成 crt格式

PEM格式证书转换为CRT格式非常简单，因为两者在本质上是兼容的（都属于文本格式的证书，基于Base64编码），通常只需要**修改文件扩展名**即可。以下是具体步骤：


### 方法1：直接修改文件扩展名
1. 找到从浏览器导出的PEM证书文件（例如 `cert.pem`）。
2. 直接将文件扩展名从 `.pem` 改为 `.crt`（例如 `cert.crt`）。

   这是因为PEM和CRT格式的证书内容结构完全一致（都是以 `-----BEGIN CERTIFICATE-----` 开头，以 `-----END CERTIFICATE-----` 结尾的Base64编码文本），只是文件扩展名不同。大多数系统和工具（包括Java的密钥库）会识别这种格式。


### 方法2：使用OpenSSL工具转换（可选，用于验证）
如果需要明确通过工具转换（例如验证证书完整性），可以使用 `openssl` 工具：

1. 在Linux/macOS终端或Windows的WSL中执行以下命令：
   ```bash
   openssl x509 -in 输入证书.pem -out 输出证书.crt
   ```
   例如：
   ```bash
   openssl x509 -in updates.jenkins.io.pem -out updates.jenkins.io.crt
   ```

2. 命令说明：
   - `x509`：指定处理X.509格式证书（最常用的证书格式）。
   - `-in`：输入的PEM格式证书路径。
   - `-out`：输出的CRT格式证书路径。

执行后会生成一个 `.crt` 格式的证书，内容与原PEM文件完全一致。


### 后续操作（在Jenkins容器中导入证书）
转换为CRT格式后，需要将证书导入Jenkins使用的Java密钥库（JKS），以解决SSL证书信任问题：

1. 进入Jenkins容器：
   ```bash
   kubectl exec -it <jenkins-pod-name> -- /bin/bash
   ```
   （替换 `<jenkins-pod-name>` 为你的Jenkins Pod名称，例如 `jenkins-7747d99db9-9ptl4`）

2. 确认Java密钥库位置（通常在JRE的 `lib/security/cacerts`）：
   ```bash
   KEYSTORE=$JAVA_HOME/lib/security/cacerts
   ```

3. 导入CRT证书到密钥库（默认密码为 `changeit`）：
   ```bash
   keytool -import -alias jenkins-update -keystore $KEYSTORE -file /path/to/你的证书.crt -trustcacerts
   ```
   - 替换 `/path/to/你的证书.crt` 为CRT证书在容器内的路径（可通过 `kubectl cp` 上传证书到容器）。
   - 执行时输入默认密码 `changeit`，并确认信任证书（输入 `yes`）。

4. 重启Jenkins容器使证书生效：
   ```bash
   kubectl delete pod <jenkins-pod-name>
   ```
   （Kubernetes会自动重建Pod，新的证书配置会生效）


通过以上步骤，Jenkins将信任目标HTTPS站点的证书，解决“PKIX path building failed”的SSL证书问题。

# 9.容器内的 jenkins 用户没有 root 权限

```sh
# jenkins容器内
jenkins@jenkins-7747d99db9-9ptl4:/opt/java/openjdk$ chmod 777 /opt/java/openjdk/lib/security/cacerts
chmod: changing permissions of '/opt/java/openjdk/lib/security/cacerts': Operation not permitted
jenkins@jenkins-7747d99db9-9ptl4:/opt/java/openjdk$ sudo chmod 777 /opt/java/openjdk/lib/security/cacerts
bash: sudo: command not found
```
在 Jenkins 容器中出现 `Operation not permitted` 或 `sudo: command not found` 错误，是因为容器内的 `jenkins` 用户**没有 root 权限**，且大多数精简容器（如基于 Alpine 或 slim 版本的镜像）默认不安装 `sudo` 工具。要解决 `cacerts` 证书文件的权限问题，需通过**容器外的 root 权限**或**重新构建容器镜像**来处理。


### **方法 1：通过宿主机直接修改容器内文件权限（推荐）**
在宿主机上通过 `nsenter` 或 `chroot` 工具直接访问容器的文件系统，以 root 权限修改 `cacerts` 权限。

#### **步骤 1：找到 Jenkins 容器的 PID**
```bash
# 在宿主机执行，获取 Jenkins 容器的 PID
POD_NAME=$(sudo kubectl get pods -n jenkins -o jsonpath='{.items[0].metadata.name}')  # 替换命名空间（-n 后）
CONTAINER_ID=$(sudo kubectl describe pod $POD_NAME -n jenkins | grep "Container ID" | awk '{print $3}' | cut -d '/' -f 3)
PID=$(docker inspect -f '{{.State.Pid}}' $CONTAINER_ID)
```

#### **步骤 2：以 root 权限进入容器的文件系统**
```bash
# 使用 nsenter 进入容器的命名空间（获得 root 权限）
sudo nsenter -t $PID -m -u -i -n -p /bin/bash
```
执行后，你会以 root 身份进入容器的文件系统。

#### **步骤 3：修改 `cacerts` 权限**
```bash
# 容器内的 cacerts 路径（与 Jenkins 容器内路径一致）
CACERTS_PATH="/opt/java/openjdk/lib/security/cacerts"

# 修改权限为可读（确保 jenkins 用户能访问）
chmod 644 $CACERTS_PATH

# 验证权限
ls -l $CACERTS_PATH
```

#### **步骤 4：退出并重启容器**
```bash
exit  # 退出 nsenter 环境
kubectl restart pod $POD_NAME -n jenkins  # 重启 Jenkins Pod
```


### **方法 2：重新构建 Jenkins 镜像，添加 root 权限**
如果需要长期在容器内拥有 root 权限（不推荐生产环境），可重新构建 Jenkins 镜像，将 `jenkins` 用户改为 root。

#### **步骤 1：创建 Dockerfile**
```dockerfile
# 基于你当前的 Jenkins 镜像（如 jenkins/jenkins:lts-jdk17）
FROM jenkins/jenkins:lts-jdk17

# 切换为 root 用户
USER root

# 可选：安装 sudo（如果需要）
RUN apt-get update && apt-get install -y sudo && rm -rf /var/lib/apt/lists/*

# 给 jenkins 用户添加 sudo 权限（可选）
RUN echo "jenkins ALL=(ALL) NOPASSWD:ALL" >> /etc/sudoers

# 切换回 jenkins 用户（保持镜像默认行为，仅在需要时手动切换 root）
USER jenkins
```

#### **步骤 2：构建并推送镜像**
```bash
# 构建镜像
docker build -t my-jenkins:root .

# 推送到 K3s 可访问的镜像仓库（如本地仓库）
docker tag my1-jenkins:root localhost:5000/my1-jenkins:root
docker push localhost:5000/my1-jenkins:root 
```

#### **步骤 3：修改 Jenkins 部署文件（jenkins-deploy.yaml）**
将镜像替换为你构建的 `my-jenkins:root`：
```yaml
spec:
  containers:
  - name: jenkins
    image: localhost:5000/my-jenkins:root  # 替换为你的镜像
```
重新部署：`kubectl apply -f jenkins-deploy.yaml -n jenkins`


### **方法 3：直接在容器内以 root 身份执行命令（临时）**
如果只是需要导入证书，可在宿主机上通过 `kubectl exec` 直接以 root 身份执行命令（无需进入容器）：
```bash
# 在宿主机执行，直接以 root 身份导入证书（假设证书已上传到容器的 /tmp/tsinghua.crt）
kubectl exec -it -n jenkins $POD_NAME -- sh -c '
  keytool -import \
    -alias tsinghua-jenkins \
    -file /tmp/tsinghua.crt \
    -keystore /opt/java/openjdk/lib/security/cacerts \
    -storepass changeit \
    -noprompt
'
```
- 此命令会直接以 root 权限在容器内执行（`kubectl exec` 默认以 root 身份运行，除非镜像指定了非 root 用户）。
- 若提示权限不足，需结合方法 1 先修改 `cacerts` 权限。


### **关键说明**
- **容器安全原则**：Jenkins 容器默认以非 root 用户（`jenkins`）运行，这是安全最佳实践，尽量避免长期使用 root 权限。
- **证书导入本质**：`keytool` 命令需要对 `cacerts` 文件有**写入权限**，只需确保 `cacerts` 的权限为 `644`（root 可写，其他用户可读）即可，无需 `777`（过松的权限）。
- **验证结果**：导入证书后，可通过以下命令检查是否成功：
  ```bash
  kubectl exec -it -n jenkins $POD_NAME -- keytool -list -keystore /opt/java/openjdk/lib/security/cacerts -storepass changeit | grep tsinghua
  ```

通过以上方法，即可解决权限问题并成功导入证书，最终正常安装 `Kubernetes Plugin`。

```bash
  -alias tsinghua-jenkins \

```

# 11.重启 Kubernetes Pod
kubectl 没有直接的 restart 命令来重启 Pod。要重启 Kubernetes Pod，有以下几种方法：

### 方法 1：删除 Pod（推荐）

Kubernetes 会自动重新创建 Pod（如果它由 Deployment、StatefulSet 等管理）：
kubectl delete pod jenkins-5495886c9-c5qdp -n jenkins

Pod 会被控制器（如 Deployment）自动重建。

### 方法 2：使用 rollout restart（适用于 Deployment）

如果 Pod 是由 Deployment 管理的，可以滚动重启：
kubectl rollout restart deployment jenkins -n jenkins

这会优雅地重启所有 Pod，而不是直接删除。

### 方法 3：修改 Pod 的注解（强制重启）

通过修改 Pod 的注解触发重启（适用于非 Deployment 管理的 Pod）：
kubectl annotate pod jenkins-5495886c9-c5qdp -n jenkins kubectl.kubernetes.io/restartedAt="$(date +%Y-%m-%dT%H:%M:%S%z)" --overwrite

如果 Pod 由控制器管理，它可能会被重新创建。

### 方法 4：使用 scale 命令（适用于 Deployment/StatefulSet）

临时缩容再扩容：
kubectl scale deployment jenkins --replicas=0 -n jenkins
kubectl scale deployment jenkins --replicas=1 -n jenkins


### 为什么 kubectl restart 不存在？

Kubernetes 的设计理念是 声明式管理，而不是直接操作 Pod。Pod 被视为 临时实体，应该由控制器（Deployment、StatefulSet 等）管理其生命周期。

### 总结

• 如果 Pod 由 Deployment 管理 → kubectl rollout restart deployment jenkins -n jenkins（推荐）
• 如果 Pod 是独立运行的 → kubectl delete pod jenkins-5495886c9-c5qdp -n jenkins
• 其他情况 → 修改注解或手动 scale
选择最适合你场景的方式！ 🚀

# 13. kubectl 如何停止

“kubectl”本身是Kubernetes的命令行工具，通常不会说“停止kubectl”，你可能是想停止Kubernetes中的相关资源，或者停止通过“kubectl proxy”启动的代理等。以下是不同情况的处理方式：
- **停止Pod**：可以使用`kubectl delete pod <pod名称>`命令来停止指定的Pod。例如，要停止名为“my - pod”的Pod，可执行`kubectl delete pod my - pod`。如果要停止某个命名空间下的所有Pod，可以使用`kubectl delete --all pods --namespace=<命名空间名称>`，如`kubectl delete --all pods --namespace=default`。
- **停止Deployment等资源**：若想停止Deployment，可以使用`kubectl delete deployments <deployment名称>`命令。若要删除某个命名空间下的所有Deployment，可执行`kubectl delete deployments --all --namespace=<命名空间名称>`。同理，对于Service等其他资源，也可以用类似方式，如`kubectl delete services <service名称>`来停止指定Service，或`kubectl delete services --all --namespace=<命名空间名称>`删除指定命名空间下的所有Service。
- **停止kubectl proxy**：如果是想停止通过`kubectl proxy`启动的代理，可以使用`kubectl proxy --stop <代理名称>`命令。例如，若代理名为“my - proxy”，则执行`kubectl proxy --stop my - proxy`来停止该代理。

此外，如果是想彻底卸载kubectl工具，在Ubuntu或Debian系统上，可以先通过`sudo kubectl delete deployments --all`等命令停止相关资源，再使用`sudo apt remove kubectl`删除kubectl软件包，最后删除配置文件等。在CentOS或RHEL系统上，可先停止资源，然后使用`sudo yum erase kubectl`卸载，再删除相关配置文件。

# 15.ubuntu上K3s卸载

在 Ubuntu 上卸载 K3s，可以按照以下步骤操作：

### 1. 停止并禁用 K3s 服务
```sh
sudo systemctl stop k3s
sudo systemctl disable k3s
```

如果是 Agent 节点（工作节点），使用：
```sh
sudo systemctl stop k3s-agent
sudo systemctl disable k3s-agent
```

### 2. 卸载 K3s 二进制和相关文件

#### 方式 1：使用官方卸载脚本
```sh
# 如果是 Server 节点（控制平面）
/usr/local/bin/k3s-uninstall.sh

# 如果是 Agent 节点（工作节点）
/usr/local/bin/k3s-agent-uninstall.sh
```

#### 方式 2：手动删除（如果没有卸载脚本）
```sh
sudo rm -rf /etc/systemd/system/k3s*
sudo rm -rf /etc/rancher/k3s/
sudo rm -rf /var/lib/rancher/k3s/
sudo rm -rf /var/lib/kubelet/
sudo rm -rf /usr/local/bin/k3s*
sudo rm -rf /usr/local/bin/kubectl
```

### 3. 清理残留网络配置

K3s 默认使用 Flannel 或 Canal 作为 CNI 插件，需清理相关网络接口和规则：
```sh
# 删除 CNI 接口
sudo ip link delete cni0
sudo ip link delete flannel.1

# 清理 iptables 规则
sudo iptables -F
sudo iptables -t nat -F
sudo iptables -t mangle -F
sudo iptables -X
```

4. 删除 Docker 容器（如果使用 Containerd）

```sh
K3s 默认使用 Containerd，但可能遗留容器：
# 如果是 Docker
sudo docker ps -aq | xargs sudo docker rm -f

# 如果是 Containerd
sudo crictl ps -aq | xargs sudo crictl rm
sudo ctr -n k8s.io containers ls -q | xargs sudo ctr -n k8s.io containers delete
```

5. 重启系统（可选）

确保所有残留进程被清除：
```sh
sudo reboot
```

### 验证卸载

检查是否还有 K3s 相关进程或文件：
ps aux | grep k3s          # 检查进程
kubectl version            # 确认 kubectl 已删除
ls /var/lib/rancher/k3s/  # 确认数据目录已清理


###  常见问题

#### 1. 卸载脚本不存在：  
   如果 /usr/local/bin/k3s-uninstall.sh 不存在，直接手动删除文件（参考步骤 2）。

#### 2. 网络残留问题：  
   如果卸载后网络异常，重启系统或手动重置网络：
   ```sh
   sudo systemctl restart networking
   ```

#### 3. 重新安装 K3s：  
   卸载完成后，如需重新安装，直接运行官方安装命令：
   ```sh
   curl -sfL https://get.k3s.io | sh -
   ```

通过以上步骤，K3s 会被彻底卸载，系统恢复干净状态。
